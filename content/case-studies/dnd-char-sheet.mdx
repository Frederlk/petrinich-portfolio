## Patterns and decisions

- I built the whole app alone: a Russian-language tabletop role-playing helper with three tools in one installable web app. A builder walks a player through a level 3 character and turns it into a live play sheet. A reader shows the group's own campaign sheets. A Dungeon Master screen holds several players' sheets side by side.
- It is a client-side app on React, TypeScript and Vite, styled with Tailwind CSS on top of Base UI. There is no router library: a small hand-written router maps six paths to five views, and the old reader address still works because links to it had already gone out to players.
- Only the home screen loads eagerly. The builder, the reader and the Dungeon Master screen are separate lazy chunks, and the builder is fetched in idle time right after the landing renders.
- Zustand holds only the choices and the tracked play state. Armor class, speed, skill totals, saves and spell numbers are never stored. Pure functions and one memoized hook derive them.
- The app installs as a PWA, and Workbox precaches the code and the fonts. Two small serverless functions on Vercel read the sheets from a private note vault. Rules data covers 10+ classes, 40+ subclasses, 10 races, 150+ spells and 40+ weapons.
- Self-check files run with Bun in a pre-commit hook and in GitHub Actions, next to Biome and TypeScript.

## Cases

**Choices that repair each other.** In the builder, race, class, subclass, background and skills all grant skills, spells or cantrips. Changing an early pick could leave an impossible later one: a skill held twice, a cantrip the race already gives, a spell the new subclass hides. I made every store setter repair the dependent fields in the same update. A new race or class resets what no longer fits. A new subclass prunes skill picks, refits background skills, trims spells to the new pool and drops a shield it does not allow. A separate validity function states what a complete step means, and a blocked Next button shows the reason. A player can go back to the first step at any point and never reaches a broken sheet.

**An engine for numbers that stack in odd ways.** Armor class comes from class tiers, a subclass formula, natural armor, a spell, a fighting style and a shield, and heavy armor can cost speed. I wrote pure functions that choose the best armor for the current ability scores, take the highest of the competing formulas, and add style and shield bonuses only where the rules allow. One weapon function picks the right ability, adds proficiency only when it applies, folds in fighting styles and rage, and returns the extra variants such as two-handed or thrown with their own damage. Modifiers to skills and initiative are data tables keyed by feature. The self-check files run the combinations.

**Rules text with the player's own numbers.** Descriptions mention save difficulty, bonuses, dice and level, and fixed numbers in text go stale for every other character. I wrote the text with placeholders and a small expression evaluator that resolves them against the current character. A dice phrase with a modifier collapses into one chip, and phrases like spell attack get the character's number right after them. A highlight pass colors game terms and turns spell names into links that open the spell. Advantage and disadvantage keep one color across the builder and the reader.

**Sharing a build as text.** Players build on phones, and the Dungeon Master needs every sheet without accounts or a database. A build exports as a short versioned string holding only the choices. Hit points and slot counters are left out and recomputed on import. The importer checks every field by shape, rejects an unknown class or race, and asks before replacing an existing character. The Dungeon Master pastes a string per player, and each opens as a read-only sheet from its own store that never writes to storage and never touches the owner's character. The party view needs no accounts and no database.
