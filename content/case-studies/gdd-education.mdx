## Patterns and decisions

- The site is a marketing site for an online school for game designers. Visitors read a course page and send a booking request, which lands in a Telegram chat. There is no database for the site itself. My part was UI polish and bug fixes, the move of hosting to a VPS, the Docker builds, DNS and analytics.
- The server is a rented VPS in Russia. Docker Compose runs four containers: the app, Umami, its PostgreSQL database and Caddy, which terminates HTTPS and renews its own certificates.
- A push to the main branch deploys through GitHub Actions. The job connects to the server, rebuilds only the app container and leaves the proxy running, so a deploy never touches certificates.
- The image runs on Node.js with a non-root user and a health check. Build-time public values and runtime secrets live in separate env files.

## Cases

**Measuring before moving off Vercel.** Some visitors in Russia saw pages without styles. A heavy page and a blocked connection look the same on screen, so the move was decided on measurements, not a guess. Reachability was tested from consumer networks of several Russian ISPs through a public probe network. Blocking is intermittent, so each run repeated many rounds. Every run also requested a control domain from the same probes, so a broken probe was not read as a blocked site. A page-weight audit ruled out the page itself. Other sites on Vercel failed too, while the control domains did not, so a new IP pool would not have helped. I moved the site to the VPS.

**A Docker build that does not trust the defaults.** Next.js bakes public environment values into the code at build time, and its standalone output leaves out static files and public assets. A container that only gets those values at runtime builds without any error, then serves a site whose canonical addresses, sitemap and share previews point to localhost and whose analytics is blocked by its own content policy. I made the image three stages: install, build, run. The public values go in as build arguments from their own env file, and the compose file stops the build with a message when the site address is missing. The static and public folders are copied in by hand. A volume created by Docker belongs to root while the app runs unprivileged, so the image cache folder is created with the right owner before the volume mounts.

**A DNS cutover that cannot fail the certificate.** The domain zone sits at Vercel with a wildcard record aimed at Vercel. Caddy asks Let's Encrypt for a certificate at startup. If the new hostname still resolves to Vercel at that moment, the challenge fails and the authority backs off for a long time. I split the cutover into two stages. First I added test hostnames with a 60 second TTL and waited for a clean answer from a public DNS check before the proxy started. Then I unlinked the domain from the Vercel project and added the www and apex records together, with the apex redirecting to www as before. I left the certificate authority records alone and planned to keep the Vercel project for at least two weeks as the way back. The zone itself stayed, because Vercel also hosts the DNS.

**Analytics that leaves with the host.** Vercel Analytics works only on Vercel, and its replacement had to be free, readable for a non-technical owner, reachable from Russia, cookie-free and a single script tag. I compared the common options on those points. Self-hosted Umami on the same server won: no extra cost, no cross-border route, a simple dashboard. The tracker script loads only when both its address and site ID are set, so local development never pings it, and the content policy allows exactly the tracker's origin. I wired three custom events: clicks on the enroll buttons with the course and the placement on the page, clicks on the Telegram contact links with their placement, and a booking-submitted event that fires only after the request was accepted, not on every click.
