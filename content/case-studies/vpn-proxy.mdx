## Patterns and decisions

The tool is one Python program that uses only the standard library, so a colleague installs nothing beyond the package. A local proxy listens on the loopback address, and a routing script is generated on every request from a plain text list of 25+ domains. An entry matches the domain itself or anything under it, with a dot check so a look-alike domain stays direct. Everything else goes direct.

At start the tool registers the script as the system proxy setting, so Chrome follows it without an extension. A cleanup block removes the setting when the tool stops. A second copy cannot disturb the first: it fails to bind the port and never touches the setting of the running one.

The proxy handles three kinds of request: the routing script, HTTPS tunnelling and plain HTTP. Each connection gets a thread, and each direction of a tunnel gets its own. The code is 450+ lines of Python with the tests and log tools, plus an installer, an uninstaller and a diagnostics script that writes a report for a colleague to send back. The build refuses to package if either check is red, and it verifies that the package holds exactly the expected top-level entries.

## Cases

**Two processes joined by a named pipe.** On a colleague's PC the VPN client treated the proxy's own loopback traffic as something to filter once the program sat on its per-application list, and the proxy hung before it could listen. I split the program in two. The front only listens locally and stays off the VPN list. The egress opens the outbound connections and is on the list, but never touches the loopback address. They talk over a named pipe, which is not network traffic, so the client's filters never see it. Both are the same executable started under two names. The front starts the egress by itself and retries for about five seconds while it unpacks. The first pipe instance is exclusive, so a second egress exits quietly.

**Closing the two sides of the bridge separately.** After the proxy closed a socket while the server was still sending, Windows sent a reset and threw away a reply the browser had already accepted. One site broke exactly on that. I rewrote the bridge so that an empty message on the pipe means end of stream from that side. Only the write half of the other socket is shut down, and everything closes after both directions finish. A test pins it: a server sends 300,000 random bytes, half-closes and drains while the client keeps sending, and the answer must arrive unchanged.

**Tests that check themselves.** Networking bugs show up under odd timing, so a green run alone proves little. The self-check starts both processes on a free port and drives them against local servers with no internet. It covers the routing script, a dead target that must answer with a 502 error, and a plain HTTP request that must reach the server in its origin form. The heaviest check sends a 5,000,000-byte random payload in uneven chunk sizes in both directions at once and compares it byte for byte. A setting points the same test at an older copy of the proxy, so I can confirm it goes red on code known to be wrong. The diagnostics script has a check of its own. A shell script extracts the embedded PowerShell, confirms it parses, runs it against a dead port and asserts what the summary must say and must not say. It also refuses non-ASCII characters in the batch files, since the Windows command shell misreads them.
