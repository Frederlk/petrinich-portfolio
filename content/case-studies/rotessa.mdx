## Patterns and decisions

- I worked with 4 other developers on the web front end of an online payments platform for businesses. The front end is one Next.js application in English and French with 80+ pages. The platform collects pre-authorized debits and bank transfers from customers' accounts.
- Server state lives in TanStack Query. The API client is generated from an OpenAPI description and covers 70+ operations. Responses follow the JSON:API format and are deserialized in query selectors, and every query key comes from one factory with a nested hierarchy.
- Zustand holds the little client state there is: the selected organization and the draft of a new contact, both persisted in the browser.
- Forms use React Hook Form with Zod, and server errors are mapped back onto the fields they belong to.
- Open detail sheets keep their state in the address bar with nuqs, and a detail query starts from the rows of the list that is already cached, so a sheet shows data before its request returns.
- next-intl serves the two languages. English sits under the French messages, so a missing French string falls back to English.

## Cases

**An application that changes shape while it is filled in.** Onboarding a business takes more than 30 screens, and the route depends on the answers. A first-time user and a user with existing organizations see different starts. An owner and a third party applying for another business take different paths. A sole proprietorship has no primary owner step, a company gets one owner page per listed owner, and a third party gets a mirrored application for the business being represented. The application builds its whole page list in one place from the live application data, and each page gets a status from the server. A progress pane groups the pages under five headers and shows each as complete, started, pending or incomplete. It lets the user jump back only to finished or started steps. Each step sends its own name and the next one to the API, so the progress is stored and the user can leave and return to where the application stopped.

**A pending screen that picks the current blocker.** After the last form, the application can still be waiting on several outside things. The owner's ID check may need to be done by a person other than the one filling the form. The bank check may still be waiting, or it may have failed and need manual entry. Then the whole application goes to compliance. Showing all of these at once would leave the user guessing which one matters. A single decider reads the application, the owners' application, the debit application and the current user, and shows exactly one state in a fixed priority. A failed bank verification comes first, with a link back to enter the bank details by hand. Next comes waiting for ID verification, with a link to copy and send to the primary owner. Then waiting for bank verification. When nothing is blocking, the application is submitted for review once, automatically, and the screen shows the expected review time.

**One permission model for pages, buttons, navigation and masked account numbers.** Staff inside an organization can read, create or edit different things, and bank numbers have to stay masked by default. Permissions load once as a map of resources and actions per organization, plus an admin role. Everything asks the same check. A page-level wrapper shows a no-access message, navigation items and action buttons hide, and account and transit numbers show masked except the last characters. The reveal toggle appears only for a user with the unmasked-read permission. The query layer ties the model to the session. A 401 on any request signs the user out, and a 403 invalidates the cached permissions so the next render reflects what the server now allows. Mutations return errors to the form instead of throwing, so the same rules cover every screen without per-page handling.
