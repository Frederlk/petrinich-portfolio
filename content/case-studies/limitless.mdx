## Patterns and decisions

- I led 1 other developer. I analysed the existing code, did the estimate and the architecture, refactored it and built the new landing page. The other developer built a few sections. The product exists in three versions of the same interface: an earliest Vite and React build in JavaScript, a Next.js 14 build in TypeScript, and a rebuild on Next.js 14 wired to a real API.
- In the rebuild, the landing page, the signed-in area and the authorization dialogs sit in separate route groups. State is the URL for dialogs and local component state for the rest, with no global store.
- TypeScript runs in strict mode. ESLint, Prettier, Husky and a GitHub Actions job for type checking and lint run on every branch.
- Tailwind CSS carries a token palette of CSS variables and custom breakpoints for small phones, over shadcn/ui style components on Radix UI.
- The chat and the player run on sample data, so the work is the interface around them: overlays on the video, a collapsing chat panel, a product strip and a tips card.

## Cases

**Sign-up and log-in as dialogs in the URL.** The landing page, the header and many buttons all had to open the log-in or sign-up dialog, and a link from outside had to open it directly. The dialogs also hand over to each other: log-in to sign-up, sign-up to the role choice, the role choice to the category picker. The open state of each dialog lives in a query parameter, kept with nuqs. A plain link opens a dialog, the back button closes it, and moving to the next dialog is two parameter changes with no route change. Each dialog sits in its own Suspense boundary, because reading the URL needs one. Sign-up validates the password strength, a real date of birth parsed with date-fns and a required terms checkbox. A fan then picks at least 3 categories, and a streamer goes to profile settings.

**One typed form and API layer.** Sign-up, log-in, profile, account, waitlist and the account deletion steps are forms with the same rules, and the backend returns its own error shapes. One hook couples React Hook Form to a Zod schema, with shared field rules and one generic input component for label, icon, password toggle and error message. An Axios service adds the API key and the token to every call. Each API function returns the same small result: a success flag, a status, a message and data, after mapping server, network and unknown errors to readable text. Screens only show a toast. T3 Env validates the base URL and the key at start, and middleware reads the token cookie to route signed-out and signed-in visitors.

**A broadcast studio where the layout is a grid you fill.** Streamers had to design what the broadcast screen shows, such as the preview, chat, follower and donor statistics and an activity graph, without a free-form canvas. A layout became a grid description plus a span for each cell, and the studio offers 9 ready-made layouts shown as thumbnails. The chosen grid and spans travel in the URL, so a refresh or a shared link keeps the design. The editor is desktop only: a phone is sent to the list of saved templates with a note to create new ones on desktop. Every cell takes one widget from a toolbox, and the start button appears only when every cell has one. The final dialog offers to start now or to add the broadcast to the schedule.

**One interface carried across three stacks.** The product had to move from a Vite prototype in plain JavaScript to a typed Next.js app and then to a rebuild with an API, without redrawing it. The second version kept every page and wrapped them in thin App Router files that only render the existing page, so all 28 routes stayed identical while the code moved to TypeScript. The third version replaced the styling, the forms and the animation (GSAP in the earlier versions, Framer Motion in the latest), and added the API layer and the CI job. The look stayed the same through every rewrite.
