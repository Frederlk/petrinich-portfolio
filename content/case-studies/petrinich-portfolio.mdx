## Patterns and decisions

- The site has no backend. Every route is static, and the content is JSON and MDX parsed with Zod when the app loads, so a bad edit fails the build.
- Wording lives in one place. The site, the CV PDF, the GitHub profile and the LinkedIn text all read the same content, and nothing is retyped by hand.
- Numbers are computed, not typed. Years of experience, project and technology counts come from the data through tokens in the text, and an unknown token fails the build. The technology counts use the same rows the work table lists, so the two pages cannot disagree.
- One table describes each page's Markdown and JSON twin. Link headers, content negotiation, page metadata, the sitemap and the machine-readable indexes all read that table.
- The robots file is a route handler, not the built-in metadata file, because it carries extra directives. Each AI crawler gets its own group with explicit access: a bot with its own group never reads the general one.
- The same rule checks run in an edit hook, in pre-commit and in CI, so one definition covers three gates. A fresh agent reviews a change, never the one that wrote it.
- CI is locked down as well. Every GitHub Action is pinned to a commit, a linter runs over the workflow files, and a separate workflow reverts a push that touches protected config.

## Cases

**One source for four places.** A CV drifts when it lives in several places. The GitHub profile still said "5+ years" and linked a retired site, and LinkedIn had the wrong city. I made the content files the only source of wording and built four renderers on top of them. The site reads them directly. The CV PDF is printed from the print view of the CV page through headless Chrome, and a script fails the PDF run on a third page or a Type3 font. When a staged file feeds that page, the pre-commit step reprints the PDF and stages it. A script renders the GitHub README and account fields; a workflow applies them after each push that changes content, and again monthly, because the year count moves with the date. LinkedIn has no write API for a personal profile, so a helper renders each field as plain text, checks it against LinkedIn's limits and remembers a hash per field. The next run shows only what changed.

**Rules that arrive when they matter.** Rules in the project instructions are read once at the start of a session and forgotten by the time an agent breaks one. I moved every rule a regex can decide into one checker, with a message that states the rule itself. A hook runs the checker before an edit lands and denies it with the rule as the reason. The same function runs on staged files in pre-commit and again in CI: three gates, one definition. The hook always exits cleanly and puts a denial in its output, so a bug in it cannot lock a session. Rules a regex cannot decide sit in path-scoped files that load only when the agent touches that area.

**Pages for readers that do not run JavaScript.** Major AI crawlers do not run JavaScript, so every fact has to be in the first HTML. An agent that fetches a page prefers Markdown. I gave every page a Markdown twin, and every work page its own. One table drives three things: response headers that point to the alternates, a rewrite that serves Markdown at the same address when the request asks for it, and an address ending in the Markdown extension for each work page. Around that sit JSON exports of the projects and technologies, a JSON Resume file, structured data and a sitemap listing every work page. Some of those exports have no confirmed reader yet. They cost almost nothing to produce, so they stay.
