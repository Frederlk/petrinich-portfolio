## Patterns and decisions

All page copy lives in Sanity and the code holds no fallback text. One cached read serves the site, and a signed webhook from Sanity expires a single cache tag on every publish, so pages stay static and refresh the moment the office publishes. One query returns the whole practitioner roster, and the directory, profiles, contact page and home page all read that one result.

The directory filters on the server and keeps its state in the URL. Groups combine with AND, values inside a group with OR, and the count beside each option is computed as if its own group were not applied. The query parameter names are the old WordPress ones, so inbound links kept working.

Clerk handles sign-in with emailed codes and no passwords, and there is no database of my own. Forms use React Hook Form with Zod, and the same rules run again on the server. 30+ test files cover the save path, the field rules, the address logic and the invite and removal handlers.

## Cases

**Practitioners can edit only their own profile.** Practitioners have public pages, and only office staff could change them. Opening the Studio to them would make each one an administrator of everything. I built a small My profile area instead. A practitioner is invited, signs in with an emailed code and sees a form with every field of the practitioner's own page, plus a preview of the public result. The server takes the profile id only from the signed-in session, never from the request, and writes that one document.

**Saves that never overwrite and never lose text.** The office can edit the same profile in the Studio while a form sits open for a long time, and one Save sends text, a photo and PDF forms through three endpoints. Every write is guarded by the revision the form was loaded with. On a mismatch the screen says the profile changed and keeps what was typed, so it can be copied. A save also deletes any unpublished Studio draft in the same transaction, so a later publish cannot undo it silently. The three steps run in order. If the photo fails, the text stays saved and a status line says what went through.

**A renamed profile address keeps working for 12 months.** Profile addresses are linked from search results and bookmarks, so a rename must not produce a 404. The redirect also has to be a real HTTP status, which a page behind a loading screen cannot send. The old address is stored with the time it was retired, kept for 12 months, up to 10 per person. A gate that runs before the page renders decides before the page renders: a known address passes, a retired one gets a temporary redirect to the current one, and an unknown one gets a real 404. A short-lived memo of the roster addresses and a negative cache keep a flood of made-up addresses from hammering the CMS.

**Invite and remove logins from the CMS.** The office needs to give a practitioner a login and take it away, but the login service knows nothing about the CMS. An Invite practitioner action in the Studio writes a small request document under the Studio user's own session, so being signed into the CMS is the access check. The same signed webhook picks the request up and claims it once. It checks the profile exists, which a draft is enough for, refuses an address that already has an account, creates the invitation and writes the result back, and the Studio dialog shows the answer without a reload. Removal is state-based. The handler re-reads the CMS and deletes the login only if neither the published document nor its draft exists, so unpublishing keeps the login and deleting removes it.
