## Patterns and decisions

- Each home, cart and products section has its own Sanity singleton document and its own GROQ query. A section is a server component. It starts the fetch and hands the promise to a view through Suspense, with a skeleton for each section.
- One fetch function has three cache modes. The default revalidates every 60 seconds. Draft mode reads drafts with a token and no cache.
- The cart lives in the browser. Products are sold in packs, 250 units by default, and quantities are rounded to whole packs.
- Types for the Sanity content are generated by Sanity typegen, so queries and views share them.
- Environment variables are declared once with the T3 Env schema. Server action input is parsed with Zod through next-safe-action.
- The site uses React Compiler.

## Cases

**One pack price in four places.** Square line items take a price per unit and a quantity, but the shop sells packs. A small rounding gap would make the cart total differ from the charge. I wrote one set of helpers for the pack size, the pack count and the quantity rounding. The product page, the cart card, the cart total and the Square payment link all call them. The payment link sends the pack price divided by the pack size as the unit price, and the pack count times the pack size as the quantity, using the same calculation as the cart total.

**A site the client edits that still renders when the CMS is empty.** The client changes every text and image in Sanity Studio, which is embedded in the site. The page must not break when a document is missing. The schema has more than 20 document types, and a custom desk tree gives each section a singleton. Every section has a hard-coded fallback object, and a helper merges it with whatever Sanity returns. Draft mode with Visual Editing lets the client click a block on the page and edit it in place. I built the schema, the desk structure, the fetch layer and the section views.

**Hosted checkout and a verified webhook.** The shop needed card payments without handling card data. The cart calls a server action. The action validates the input with Zod, creates a Square Payment Link and redirects the browser to Square's hosted page. Square also collects the shipping address and takes the coupon code there. An idempotency key goes with each attempt. The success page clears the cart. The webhook route reads the raw body, checks Square's HMAC signature and answers 403 on a wrong one. A processing failure returns 500, so Square retries.
